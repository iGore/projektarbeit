\section{Evaluation am Fallbeispiel} \label{evaluation}

Dieses Kapitel beschreibt die Durchführung der Pipeline am konkreten Migrationsszenario, die Befunde des I/O-Vergleichs zwischen Quell- und Zielsystem, die daraus abgeleiteten zwei Skill-Iterationen, einen dritten Durchlauf zur Nachprüfung sowie die Grenzen der Aussagekraft dieser Befunde.

\subsection{Auswahl des Szenarios und Quell-Moduls}

Demonstrationsszenario ist die in Kapitel~\ref{implementierung} beschriebene Migration des Node.js-basierten Lizenz-Checkers \texttt{davglass/license-checker} nach Go. Das Werkzeug ist klein genug für einen vollständigen Durchstich durch alle Pipelinephasen, lässt sich in klar abgegrenzte Funktionalitäten zerlegen und besitzt ein hinreichend definiertes Ein- und Ausgabeverhalten für einen I/O-Vergleich.

\subsection{Durchführung des spezifikationsgetriebenen Workflows}

Die Pipeline wurde dreimal vollständig ausgeführt. Der erste Durchlauf lieferte kein lauffähiges Binary und führte zur ersten Skill-Iteration (Abschnitt~\ref{sec:builder-gap}). Der zweite Durchlauf ist Grundlage des manuellen I/O-Vergleichs (Abschnitt~\ref{sec:io-befunde}) und der zweiten Skill-Iteration (Abschnitt~\ref{sec:datafluss-gap}). Der dritte Durchlauf diente der Nachprüfung mit der weiterentwickelten Pipeline (Abschnitt~\ref{sec:dritter-lauf}). In jedem Durchlauf steuerte der Orchestrator die Übergaben zwischen den sechs Fachagenten (Analyzer, Spec-Writer, Architect, Planner, Task Decomposer, Builder) sowie dem Verifier als unabhängiger Prüfinstanz. Die ersten beiden Durchläufe nutzten noch Sourcebot als Code-Intelligence-MCP \parencite{sourcebotdocs}, mit einem entsprechenden Nutzungsleitfaden als Skill. Die in Kapitel~\ref{implementierung} beschriebene Umstellung auf CodeGraphContext erfolgte danach und gilt für den dritten Durchlauf. Die folgende Beschreibung bezieht sich auf die ersten beiden Durchläufe.

In Phase~1 erschloss der Analyzer die Quellbasis und erzeugte \texttt{ANALYSIS.md} und \texttt{USE-CASES.md}. Die ausgeführte Pipeline identifizierte acht Funktionalitäten: F-001 (CLI-Optionsmodell und Normalisierung), F-002 (Abhängigkeitsgraph-Laden und Traversierungssteuerung), F-003 (Abflachen des Graphen zu einem Modulinventar), F-004 (Lizenzerkennungs- und Normalisierungspipeline), F-005 (Filterung, Paketeinschränkung und Policy-Exits), F-006 (Ausgabe-Rendering und Persistenz), F-007 (Custom-Format und JSON-Konfigurationsladung) sowie F-008 (Stack-Utility-Lifecycle). Alle acht wurden vom Analyzer als \emph{ready} klassifiziert. Der Orchestrator löste daraufhin acht parallele Spec-Writer-Läufe aus, einer pro Funktionalität, und sammelte die Ergebnisse in \texttt{SPECS.md}.

In Phase~2 leitete der Architect aus der konsolidierten Spezifikationsbasis eine Go-Zielarchitektur ab: Paketstruktur, Fehlerbehandlungskonventionen, geeignete Standardbibliotheksfunktionen und externe Go-Bibliotheken wurden mit Context7-Unterstützung festgelegt. Der Planner überführte diese Entscheidungen anschließend in einen geordneten Migrationsplan. In Phase~3 zerlegte der Task Decomposer den Plan in umsetzbare Arbeitseinheiten und der Builder erzeugte Go-Zielcode, der in \texttt{BUILD.md} mit Verifikationsnachweis dokumentiert ist. Alle acht Funktionalitäten wurden vollständig durch die Pipeline geführt; anschließend folgte der manuelle Vergleich des beobachtbaren CLI-Verhaltens.

\subsection{Beispiel: Spezifikation und Zielcode im Vergleich}

Die folgenden Listings zeigen den tatsächlichen Output der Pipeline für die Funktionalität \textbf{F-004: License detection and normalization pipeline}. Listing~\ref{lst:spec} gibt einen Auszug aus der vom Spec-Writer erzeugten \texttt{SPEC.md}, Listing~\ref{lst:target} den daraus vom Builder generierten Go-Zielcode.

\begin{lstlisting}[style=codestyle, caption={Auszug aus der erzeugten SPEC.md für F-004 (License detection and normalization pipeline)}, label=lst:spec]
## Requirements

- FR-001: System MUST resolve license from metadata fields
          (`license`, `licenses`) before fallback mechanisms.
- FR-002: System MUST apply fallback precedence:
          metadata -> README-derived -> license-file-derived.
- FR-004: System MUST mark heuristically inferred values
          with trailing `*` to distinguish inferred vs direct.
- FR-005: System MUST normalize URL/file-style references
          to `Custom: <value>`.
- FR-006: File fallback MUST follow deterministic order:
          LICENSE*, LICENCE*, COPYING, README.

## Acceptance Scenario (P1)

Given a module with a valid SPDX `license` string,
When the pipeline resolves license data,
Then that SPDX value is returned without file-based fallback.

## Open Decisions

- OD-001: When `license` and `licenses` conflict, confirm
  exact legacy tie-break order from source code/tests.
- OD-002: Confirm exact fallback value when no license
  signal is found across metadata, README, and files.
\end{lstlisting}

\begin{lstlisting}[style=codestyle, language=Go, caption={Vom Builder erzeugter Go-Zielcode: license/detect.go}, label=lst:target]
package license

import "theseus/target/internal/core"

type Detector struct{}

func (Detector) Resolve(
    input core.ModuleLicenseInput,
) (core.NormalizedLicenseValue, string) {

    // FR-001/FR-002: metadata first
    if v := resolveFromMetadata(input); v != "" {
        return core.NormalizedLicenseValue(v), ""
    }
    // FR-002: README fallback
    if v, _ := normalize(input.ReadmeText); v != "" {
        return core.NormalizedLicenseValue(v), "README"
    }
    // FR-002/FR-006: deterministic file fallback
    for _, candidate := range orderedCandidates(
        input.CandidateFiles,
    ) {
        if v, _ := normalize(candidate.Content); v != "" {
            return core.NormalizedLicenseValue(v),
                   candidate.Name
        }
    }
    // OD-002: sentinel until legacy parity confirmed
    return core.NormalizedLicenseValue("UNKNOWN"), ""
}
\end{lstlisting}

Die Listings zeigen den tatsächlichen Output der ausgeführten Pipeline. Die im Ausschnitt sichtbaren Anforderungen FR-001, FR-002 und FR-006 sind über Inline-Kommentare direkt auf Implementierungsschritte im Go-Zielcode abbildbar: Die Fallback-Reihenfolge (Metadata $\to$ README $\to$ Dateien) entspricht den in der Spezifikation festgelegten Teilschritten. Die offene Entscheidung OD-002 ist als Kommentar am Rückgabewert \texttt{UNKNOWN} markiert. Das zeigt, wie der spec-getriebene Ansatz Unsicherheiten aus der Analyse nicht wegabstrahiert, sondern als offene Entscheidung bis in den Zielcode trägt, bis sie manuell oder durch weitere Analyse aufgelöst werden kann.

\subsection{Bewertungsrahmen: Qualitätsdimensionen der erzeugten Artefakte} \label{sec:bewertungsrahmen}

Die Evaluation des PoC erstreckt sich auf zwei Artefaktklassen: die generierten Spezifikationen und den erzeugten Go-Zielcode. Für beide werden im Folgenden die maßgeblichen Qualitätsdimensionen beschrieben. Systematisch geprüft wurde im PoC nur die Korrektheit über den I/O-Vergleich (Abschnitte~\ref{sec:funktionale-validierung} und~\ref{sec:dritter-lauf}). Die übrigen Dimensionen bilden den Bewertungsrahmen für die in Kapitel~\ref{fazit} skizzierte Weiterentwicklung und wurden nicht quantitativ erhoben.

\subsubsection{Qualitätsdimensionen der Spezifikationsartefakte}

Wie \textcite{midolo2026promptguidelines} zeigen, sind für hochwertige Spezifikationen vor allem explizite I/O-Angaben, Vor- und Nachbedingungen sowie Beispiele relevant. Daraus ergeben sich folgende Dimensionen:

\textbf{Präzision:} Sind I/O-Formate, Datentypen, Vor- und Nachbedingungen sowie Akzeptanzszenarien so konkret formuliert, dass der Builder ohne Rückfragen implementieren kann? Vage oder implizite Anforderungen gelten als Qualitätsmangel.

\textbf{Rückverfolgbarkeit:} Verweist jede funktionale Anforderung auf eine konkrete Evidenzstelle in \texttt{ANALYSIS.md}? Lücken in der Rückverfolgbarkeit erschweren die Fehlersuche bei Abweichungen zwischen Quell- und Zielverhalten.

\textbf{Vollständigkeit:} Deckt die Spezifikation alle in \texttt{USE-CASES.md} identifizierten Funktionalitäten ab? Fehlende Funktionalitäten bedeuten blinde Flecken in der Neuimplementierung.

\textbf{Offene-Fragen-Behandlung:} Werden unklare Punkte explizit als offene Fragen markiert statt still angenommen? Implizite Annahmen gelten als Qualitätsmangel im Sinne des Spec-Quality-Skills.

Für die Aussagekraft der Evaluation ist zudem relevant, wie transparent Prompt- und Kontextentscheidungen dokumentiert werden, da \textcite{korn2026reportingprompting} deutliche Reproduzierbarkeitslücken in der SE-Forschung aufzeigen.

\subsubsection{Qualitätsdimensionen des Zielcodes} \label{sec:qualitaet-code}

\textbf{Korrektheit (I/O-Äquivalenz):} Erzielt der generierte Go-Code für alle definierten I/O-Testfälle dieselben Ausgaben wie die Quellimplementierung? Dieses Kriterium ist formal als I/O-Äquivalenz definiert: Für identische Eingaben müssen Quell- und Zielimplementierung identische Ausgaben produzieren. Eniser et al.\ entwickeln mit Fluorine einen cross-language Differenzfuzzer, der diese Äquivalenz automatisch prüft; im PoC erfolgte der Abgleich an ausgewählten Testfällen, in den ersten beiden Durchläufen manuell und mit der schwächeren Befundklasse \emph{semantisch identisch}, im dritten skriptgestützt und byteweise \parencite{eniser2025realworld}.

\textbf{Vollständigkeit (Feature Parity):} Sind alle identifizierten Funktionalitäten im Zielcode implementiert? Nicht abgedeckte Funktionalitäten gelten als Parity-Lücken.

\textbf{Wartbarkeit:} Ist der generierte Code lesbar, strukturiert und dokumentiert? Als Maßstab dienen messbare Wartbarkeitskriterien wie Methodenlänge, zyklomatische Komplexität und Kommentartiefe \parencite{nunes2025maintainability}. Code, der zwar korrekt, aber kaum wartbar ist, gilt als Qualitätsmangel.

\textbf{Idiomatizität:} Folgt der Code den Konventionen des Zielstacks? Für Go bedeutet das: explizite Fehlerbehandlung, stdlib-first, kurze Receiver-Namen, Interfaces an der Consumer-Seite. Der Go-Craftsman-Skill operationalisiert diese Kriterien als implementierungsbegleitende Checkliste. Dass LLMs auch bei korrekt übersetztem Code in 1--15 Prozent der Fälle nicht-idiomatischen Stil produzieren, belegen Eniser et al.\ mit einer Clippy-Analyse generierter Rust-Übersetzungen \parencite{eniser2025realworld}; ein analoges Muster ist für Go-Generierungen plausibel, wurde im PoC über \texttt{go vet} hinaus aber nicht systematisch untersucht.

\textbf{Rückverfolgbarkeit zur Spec:} Lässt sich jeder implementierte Codeabschnitt auf ein Akzeptanzszenario in \texttt{SPEC.md} zurückführen? Die Inline-Kommentare im generierten Code (z.\,B. \texttt{// FR-001/FR-002}) ermöglichen diese Prüfung direkt im Code-Review.

\subsection{Funktionale Validierung und Feature Parity} \label{sec:funktionale-validierung}

Die funktionale Validierung folgt einem Black-Box-Ansatz im Sinne des klassischen \emph{Differential Testing}, bei dem zwei Implementierungen desselben Programms mit identischen Eingaben ausgeführt und ihre Ausgaben verglichen werden, ohne dass Annahmen über die interne Struktur erforderlich sind \parencite{mckeeman1998differentialtesting}. Für die LLM-gestützte Code-Übersetzung hat dieses Vorgehen unter dem Begriff der I/O-Äquivalenz aktuelle Aufmerksamkeit erfahren \parencite{eniser2025realworld}. In der vorliegenden Arbeit werden Quell- und Zielimplementierung als geschlossene CLI-Werkzeuge betrachtet und an identischen Eingaben gegeneinander ausgeführt; die Beurteilung der Feature Parity ergibt sich aus dem Vergleich der beobachtbaren Ausgaben. Als Quellsystem dient \texttt{davglass/license-checker}, dessen Einsatzzwecke von der Auflistung aller Dependency-Lizenzen über die Erzeugung maschinenlesbarer Compliance-Artefakte bis hin zur Policy-Durchsetzung in CI-Umgebungen reichen; sie verteilen sich auf die acht vom Analyzer identifizierten Funktionalitäten. Statische Analysen und Tests des Zielsystems (\texttt{go build}, \texttt{go vet}, \texttt{go test}) dienen lediglich als Vorab-Filter, der prüft, ob das Binary des Zielsystems baut und die vom Builder abgeleiteten Akzeptanztests besteht; die Aussage über die Verhaltensgleichheit gegenüber dem Quellsystem entsteht erst durch den nachgelagerten I/O-Vergleich.

\subsubsection{Verifikationsverfahren pro Funktionalität}

Damit Abweichungen sich nicht in einem Gesamtoutput verschleiern, wird der Vergleich getrennt nach den acht identifizierten Funktionalitäten geführt. Referenz ist dabei ausschließlich die beobachtete Ausgabe des Quellsystems. Die Golden-Files, die der Builder in Phase~3 für seine Integrationstests erzeugt hat (etwa \texttt{render\_export} oder \texttt{license\_resolution\_compat}), sind aus der Spezifikation abgeleitet und damit kein unabhängiger Maßstab; sie werden höchstens als Sammlung von Eingabeszenarien wiederverwendet. Das ursprünglich geplante Verfahren pro Funktionalität und sein Umsetzungsstand stehen in Anhang~\ref{anhang:plan}. Im zweiten Durchlauf wurde davon die in Tabelle~\ref{tab:io-befunde} dokumentierte Teilmenge durchgeführt.

\subsubsection{Befunddokumentation und Fehlerzuordnung}

Pro Vergleichsfall wird einer von vier Befunden festgehalten:
\begin{itemize}
  \item \emph{identisch}: Stdout, Stderr und Exit-Code stimmen byteweise überein;
  \item \emph{semantisch identisch}: Exit-Code, Modulmenge und Lizenzwerte stimmen überein, Unterschiede bestehen nur in Feldreihenfolge, Leerraum oder Zeilenumbrüchen;
  \item \emph{erwartete Abweichung}: Unterschiede, die auf den Werkzeugrahmen und nicht auf die Fachlogik zurückgehen, etwa Versionsangabe oder Layout des Hilfetexts;
  \item \emph{abweichend}: jede weitere Abweichung, mit konkreter Beschreibung.
\end{itemize}
Die Klasse \emph{semantisch identisch} ist bewusst schwächer als die in Abschnitt~\ref{sec:qualitaet-code} definierte I/O-Äquivalenz; Abschnitt~\ref{sec:validitaet} diskutiert die Folgen. Tritt eine Abweichung auf, wird sie auf die ursprüngliche Pipelinephase zurückgeführt. Liegt der Befund daran, dass die zugrunde liegende \texttt{SPEC.md} eine relevante Anforderung nicht eindeutig festgelegt hat, gilt der Befund als \emph{Spec-Lücke}; war die Anforderung dort eindeutig formuliert, der Zielcode weicht aber dennoch ab, gilt er als \emph{Builder-Fehler}. Diese Zuordnung ist diagnostisch wichtig, weil sie zeigt, an welcher Stelle der Pipeline (Spezifikations- oder Implementierungsphase) eine Korrektur ansetzen muss, und damit die Aussagekraft der Verifikation über reine Funktionsergebnisse hinaus erhöht.

Der Vergleich wurde im zweiten Durchlauf bewusst manuell geführt, weil die acht Funktionalitäten überschaubar sind und der diagnostische Wert in der Phasenzuordnung liegt, nicht in der Größe der Vergleichsmenge. Für den dritten Durchlauf wurde er als Skript wiederholbar gemacht (Anhang~\ref{anhang:skript}). Eine vollständig automatisierte Variante über einen Cross-Language-Differenzfuzzer wie Fluorine~\parencite{eniser2025realworld} ist für die Bachelorarbeit vorgesehen.

\subsubsection{Durchführung und Befunde des manuellen Vergleichs (zweiter Durchlauf)} \label{sec:io-befunde}

Der Vergleich wurde nach einem festen Schema pro Funktionalität durchgeführt. Für jeden Vergleichsfall wurde ein minimales Node.js-Eingabeprojekt mit den für die jeweilige Funktionalität relevanten Eigenschaften vorbereitet (\texttt{package.json} mit definierten Abhängigkeiten und Lizenzfeldern, einmaliges \texttt{npm install}). Anschließend wurde das Quellsystem über \texttt{npx -{}-yes license-checker} mit den vereinbarten Argumenten im Eingabeverzeichnis ausgeführt; \texttt{stdout}, \texttt{stderr} und Exit-Code wurden festgehalten. Das aus \texttt{target/cmd/licensechecker} kompilierte Go-Binary wurde mit denselben Argumenten im selben Verzeichnis ausgeführt und analog protokolliert. Die Ausgaben wurden gegeneinandergestellt und einer der vier Befundklassen zugeordnet; Abweichungen wurden als \emph{Spec-Lücke} oder \emph{Builder-Fehler} klassifiziert.

Für den Durchstich wurden zehn Vergleichsfälle vorbereitet. Sie decken sieben der acht Funktionalitäten ab; F-008 ist ein interner Hilfsdatentyp ohne CLI-Oberfläche. Die dargestellten Befunde beziehen sich auf den zweiten Durchlauf, also den nach der in Abschnitt~\ref{sec:builder-gap} dokumentierten ersten Skill-Iteration. Der erste Durchlauf erzeugte kein lauffähiges Binary; mit einem manuell ergänzten Entry-Point wurde sie nur stichprobenartig geprüft (Abschnitt~\ref{sec:builder-gap}), diese Befunde sind nicht tabellarisch erfasst. Die Befunde lassen drei Aussagen zu, deren Reichweite Abschnitt~\ref{sec:validitaet} einordnet. Erstens verhält sich die CLI-Oberfläche des Zielsystems erwartungsgemäß: \texttt{-{}-version} und \texttt{-{}-help} liefern jeweils eine Ausgabe und einen sinnvollen Exit-Code; die Divergenzen gegenüber dem Quellsystem sind auf der Ebene des Werkzeugrahmens (\texttt{cobra} statt \texttt{commander.js}) zu erklären und nicht funktional. Zweitens sind sieben der acht inhaltlichen Vergleichsfälle semantisch identisch, verteilt über die Funktionalitäten F-002 bis F-007. Der verbleibende Befund auf F-005 \texttt{-{}-onlyAllow MIT} ist weder ein Verkabelungs- noch ein Renderdefekt, sondern eine Lücke der Spezifikation; Abschnitt~\ref{sec:datafluss-gap} arbeitet ihn auf. Drittens haben die Integrationstests im Builder-Output keinen der Defekte erfasst: Alle Tests waren grün, ebenso \texttt{go build ./...} und \texttt{go vet ./...}. Die Defekte zeigten sich erst, als das End-to-End-Verhalten gegen das Quellsystem geprüft wurde. Für dieses Fallbeispiel stützt das die Annahme, die dem Differential Testing zugrunde liegt (Abschnitt~\ref{sec:funktionale-validierung}): Die funktionale Korrektheit eines aus Spezifikationen generierten Systems lässt sich erst an beobachtbaren Ausgaben verlässlich beurteilen und nicht aus dem Bestehen lokaler Test- und Build-Schritte ableiten.

\subsection{Skill-Iterationen und Nachprüfung} \label{sec:iterationen}

Aus den Befunden wurden zwei Anpassungen der Pipeline-Skills abgeleitet. Ein dritter Durchlauf prüfte anschließend, ob die Defekte mit der weiterentwickelten Pipeline noch auftreten.

\subsubsection{Erste Skill-Iteration: Verkabelungslücke des Builder-Outputs} \label{sec:builder-gap}

Im ersten Pipelinedurchlauf trat ein methodisch relevanter Befund auf, der den in Abschnitt~\ref{sec:agenten} eingeführten Verifier-Mechanismus direkt betrifft: Der Builder-Agent hatte für die acht Funktionalitäten Library-Code unter \texttt{target/internal/} sowie Integrationstests unter \texttt{target/test/integration/} erzeugt, jedoch keinen lauffähigen Entry-Point in Form eines \texttt{main.go} unter \texttt{target/cmd/}. Damit fehlte die End-to-End-Verkabelung der Stufen \emph{Loader}~$\rightarrow$~\emph{Flatten}~$\rightarrow$~\emph{License-Resolution}~$\rightarrow$~\emph{Filter}~$\rightarrow$~\emph{Render}, ohne die ein I/O-Vergleich gegen das Quellsystem nicht möglich gewesen wäre. Ein zur Überbrückung manuell ergänztes \texttt{main.go} bestätigte den Befund in einer Stichprobe: Die geprüften Aufrufe, die einen vollständigen Pipeline-Durchstich erfordern, erkannten ausschließlich das Root-Modul; zusätzlich produzierten die Render-Stufen für \texttt{-{}-json}, \texttt{-{}-csv} und Markdown jeweils ein vom Quellsystem abweichendes Schema, und \texttt{-{}-customPath} wurde vollständig ignoriert.

Auffällig ist, dass dieser Mangel vom Verifier in der ursprünglichen Konfiguration nicht erkannt wurde: \texttt{go build ./...} und \texttt{go vet ./...} laufen auch ohne Entry-Point fehlerfrei durch, weil die Werkzeuge nur die vorhandenen Pakete kompilieren. Die Verifier-Checkliste enthielt keinen expliziten Check auf ein lauffähiges Binary für CLI-orientierte Zielsysteme. Eine Phase galt damit artefaktbasiert als bestanden, obwohl ein für die Akzeptanzszenarien zentrales Artefakt fehlte. Bemerkenswert ist, dass hier nicht die Selbstprüfung des Orchestrators versagte, sondern der getrennte Verifier, weil seine Checkliste unvollständig war. Der Befund zeigt damit, dass die Rollentrennung allein nicht genügt: Die Prüfkriterien müssen auch das beobachtbare End-to-End-Verhalten umfassen und nicht nur die Existenz und Struktur von Artefakten.

Als unmittelbare Konsequenz wurden die Pipeline-Skills entlang der natürlichen Pipeline-Flussrichtung erweitert, statt einzelne Agentenprofile mit Spezialfällen zu beschweren. Im \texttt{cli-analyzer}-Skill wurde verankert, dass \texttt{ANALYSIS.md} für jedes Output-Format des Quellsystems eine reale, durch tatsächliche Ausführung gewonnene Beispielausgabe (\emph{Golden Output Snippet}) sowie eine explizite \texttt{End-to-End-Pipeline}-Sektion enthalten muss; das End-to-End-Verhalten ist damit aber bewusst keine eigene Funktionalität, sondern eine Architekturanforderung. Im \texttt{go-architect}-Skill wurde im Gegenzug die Pflicht eines verbindlichen \texttt{Composition-Root}-Abschnitts in \texttt{ARCHITECTURE.md} verankert, der Entry-Point-Pfad, Stage-Sequenz, konkrete Stage-Konstruktoren, eine Flag-zu-Stage-Propagationstabelle sowie eine Akzeptanzreferenz auf die Golden Output Snippets der \texttt{ANALYSIS.md} festschreibt. Damit hat der Builder bereits aus den Architektur-Artefakten eine eindeutige Bauanleitung für \texttt{cmd/<tool>/main.go}. Im \texttt{orchestrator-completion}-Skill wurde die Phasen-Checkliste um genau diese beiden Punkte ergänzt: Phase~2 prüft das Vorhandensein des Composition Roots, Phase~3 prüft, ob das Binary baut, auf \texttt{-{}-help} und \texttt{-{}-version} reagiert und ob seine End-to-End-Ausgabe den Golden Output Snippets semantisch entspricht. Das Verifier-Profil bleibt generisch und verweist auf den Skill als verbindliche Quelle der Checkliste. Ergänzend wurde im Builder-Profil festgeschrieben, dass für CLI-orientierte Zielsysteme ein \texttt{cmd/<tool>/main.go} als Pflichtartefakt zur \texttt{BUILD.md} gehört. Alle Anpassungen wurden in den jeweiligen Skill- und Profildateien unter \texttt{.agents/skills/} und \texttt{.opencode/agents/} festgeschrieben.

Im zweiten Pipelinedurchlauf mit den erweiterten Skills traten diese Defekte nicht mehr auf. Der Builder erzeugte ohne externe Ergänzung ein lauffähiges Binary unter \texttt{target/cmd/licensechecker/main.go}, das die im Composition Root spezifizierte Stage-Sequenz instanziiert und die in der Flag-zu-Stage-Propagationstabelle festgehaltenen Konfigurationen propagiert. Die im selben Lauf produzierten I/O-Vergleichsergebnisse (Tabelle~\ref{tab:io-befunde}) zeigen die zuvor in der Stichprobe beobachteten Verkabelungs- und Schemadefekte in keinem der geprüften Fälle mehr. Das spricht dafür, dass die Skill-Erweiterung die Defektklasse und nicht nur einen Einzelfall adressiert. Ein strenger Nachweis ist es nicht: Der Vorher-Zustand wurde nur stichprobenartig erfasst, und zwischen den Durchläufen wechselte neben den Skills auch die OpenCode-Version.

\subsubsection{Zweite Skill-Iteration: Datenflusslücke der Quellrekonstruktion} \label{sec:datafluss-gap}

Der nach der ersten Iteration verbleibende Befund auf F-005 \texttt{-{}-onlyAllow MIT} weist auf eine zweite, methodisch eigenständige Defektklasse hin. Das Quellsystem bricht mit Exit-Code $1$ und der Meldung \texttt{"... is licensed under \"UNLICENSED\" which is not permitted by the -{}-onlyAllow flag"} ab; das Zielsystem hingegen verarbeitet die Eingabe ohne Policy-Verletzung weiter, weil es das deklarierte Lizenzfeld (\texttt{"license": "MIT"}) wörtlich übernimmt. Die Ursache liegt im Quellsystem in einer einzigen unbedingt wirkenden Werttransformation: In \texttt{lib/index.js} wird der Wert von \texttt{licenses} bei Paketen mit \texttt{"private": true} unabhängig vom CLI-Flag und unabhängig vom deklarierten Lizenzwert auf \texttt{UNLICENSED} gesetzt. Der dazugehörige Test (\texttt{tests/test.js}, \emph{should recognise private modules}) prüft genau dieses Verhalten an einer Fixture mit \texttt{"private": true} ohne \texttt{license}-Feld.

In der durch den Pipelinedurchlauf erzeugten Spezifikation taucht der Marker \texttt{private} mehrfach auf, jedoch ausschließlich im Kontext des Flags \texttt{-{}-excludePrivatePackages}: \texttt{ANALYSIS.md} führt ihn als Filter-Konzept; die \texttt{SPEC.md} der Filter-Funktionalität (F-005) formuliert die zugehörige FR als \emph{System MUST remove private packages when excludePrivatePackages is enabled}. Die unbedingte Werttransformation des Felds \texttt{licenses}, die ohne jedes Flag wirkt, ist in keiner \texttt{SPEC.md} erfasst. Strukturell handelt es sich also nicht um einen Rekonstruktionsfehler im engeren Sinne, sondern um eine systematische Blindstelle der bisher verwendeten Rekonstruktionsachse. Der \texttt{cli-analyzer}-Skill schreibt in seiner ersten Fassung eine Rekonstruktion \emph{entlang der CLI-Oberfläche} vor (Flag~$\rightarrow$~Verhalten~$\rightarrow$~Test). Eine flagunabhängige Werttransformation auf einem Eingabefeld liegt nicht auf dieser Achse und bleibt damit unsichtbar. Der Test, der das Verhalten prüft, wird implizit derjenigen Funktionalität zugeschlagen, in deren Flagname das Feld vorkommt.

Diese zweite Defektklasse ist abstrakt adressierbar, indem die Rekonstruktion um eine \emph{datenflussorientierte} Achse ergänzt wird. Im \texttt{cli-analyzer}-Skill wurde dafür eine zusätzliche Pflichtsektion \texttt{\#\# Input-Field Inventory} verankert. Sie betrifft jedes Eingabefeld, das das Quellsystem aus externen Quellen liest, etwa aus Konfigurations- und Manifest-Dateien, Paket-Deskriptoren, Umgebungsvariablen, Stdin oder Netzwerkantworten. Für jedes solche Feld verlangt die Sektion vier Angaben:
(a) Feldname und Quelle;
(b) Defaultpfad durch die Pipeline;
(c) jeden konditionalen Override mit Code-Quelle und auslösender Bedingung, wobei ausgewiesen wird, ob ein CLI-Flag, eine Umgebungsvariable oder ein Konfigurationsschlüssel ihn steuert oder ob er unbedingt wirkt;
(d) eine Querreferenz auf die Tests im Quellsystem, die den Override-Pfad prüfen, auch wenn deren \texttt{describe}-Block dem Namen nach zu einer anderen Funktionalität zu gehören scheint.
Für jeden unbedingten Override muss der Analyzer zusätzlich eine Probe-Fixture konstruieren, das Quellsystem darauf ausführen und das Ergebnis als weiteres \emph{Golden Output Snippet} hinterlegen. Im \texttt{orchestrator-completion}-Skill prüft Phase~1, ob dieses Inventar vorhanden und vollständig ist. Zudem muss jeder unbedingte Override als eigene FR in der \texttt{SPEC.md} derjenigen Funktionalität erscheinen, der das betroffene Ausgabefeld gehört, und nicht nur in der Funktionalität, deren CLI-Flag zufällig denselben Namensbestandteil trägt.

Methodisch ordnet sich diese zweite Iteration als orthogonale Ergänzung zur ersten ein: Die erste Iteration adressierte die \emph{Verkabelungslücke}, eine Lücke im Kontrollfluss zwischen Spezifikation und lauffähigem Binary; die zweite adressiert die \emph{Datenflusslücke} zwischen Quellverhalten und Spezifikation. Beide Defektklassen waren durch das Bestehen lokaler Test- und Build-Schritte nicht zu erkennen. Beide wurden erst durch das beobachtungsbasierte Differential Testing aufgedeckt. Und für beide wurde die Korrektur in den Pipeline-Skills verankert, ohne domänenspezifische Sonderbehandlungen in den Agentenprofilen. Der verbliebene abweichende Befund geht damit nicht auf einen unzureichenden Builder-Output zurück. Er zeigt vielmehr, dass eine ausschließlich an der CLI-Oberfläche orientierte Rekonstruktion eine benennbare Klasse von Verhaltensregeln übersieht. Ob die zweite Iteration wirkt, prüft der dritte Durchlauf.

\subsubsection{Dritter Durchlauf: Nachprüfung mit byteweisem Vergleich} \label{sec:dritter-lauf}

Der dritte Durchlauf nutzte die weiterentwickelte Pipeline. Gegenüber dem zweiten Durchlauf waren neben der zweiten Skill-Iteration drei weitere Änderungen wirksam. Erstens ersetzte CodeGraphContext Sourcebot als Code-Intelligence-MCP. Zweitens war das Quellsystem als Git-Submodul auf einem festen Stand eingebunden (Version 25.0.1). Drittens verlangten die Skills für jede Ausgabe einen byteweisen Abgleich gegen hinterlegte Referenzausgaben anstelle der Klasse \emph{semantisch identisch}; zulässige Abweichungen müssen vorab in einer \emph{Conformance Matrix} deklariert werden.

Der Analyzer zerlegte das Quellsystem diesmal in neun Funktionalitäten: CLI-Aufruf mit Hilfe und Version, Argument-Parsing und Defaults, Abhängigkeitsgraph, Lizenz- und Metadatenableitung, Filter und Lizenz-Policy, Report-Rendering, Ausgabedateien und Lizenzexport, Diagnose- und Fehlerausgaben sowie Custom-Format-Konfiguration. Dieselbe Quellbasis wurde also anders geschnitten als in den ersten beiden Durchläufen, was die Nichtdeterminiertheit der Rekonstruktion illustriert. Der Builder erzeugte ohne manuelle Ergänzung ein lauffähiges Binary unter \texttt{target/cmd/license-checker}; \texttt{go build}, \texttt{go vet} und \texttt{go test} liefen fehlerfrei durch.

Eine Einschränkung betrifft die Referenzausgaben innerhalb der Pipeline. Weil die Agenten das Quellsystem nicht ausführen dürfen, hat der Analyzer die erwarteten Ausgaben statisch aus Quellcode und Tests des Quellsystems hergeleitet und nicht aufgezeichnet. Die Conformance Matrix stuft deshalb alle Ausgabemodi als \emph{compatible} und keinen als \emph{identical} ein. Die bestandenen Tests belegen damit nur die Übereinstimmung mit hergeleiteten Erwartungen. Die Aussage über die tatsächliche Verhaltensgleichheit stammt wie zuvor aus einem Vergleich außerhalb der Pipeline.

Dieser Vergleich wurde mit dem Skript aus Anhang~\ref{anhang:skript} durchgeführt. Es führt Quell- und Zielsystem mit denselben Argumenten im selben Verzeichnis aus und vergleicht \texttt{stdout}, \texttt{stderr}, Exit-Code sowie erzeugte Dateien byteweise. Als Eingabe dienten zwei Projekte. Projekt~A enthält 158 Pakete, darunter transitive und mehrfach vorkommende Abhängigkeiten, ein Paket mit Namensraum, Entwicklungsabhängigkeiten und ein lokales Paket ohne Lizenzangabe. Projekt~B ist ein kleines Projekt, dessen Wurzelpaket \texttt{"private": true} und zugleich \texttt{"license": "MIT"} deklariert, also genau die Konstellation der Datenflusslücke. Tabelle~\ref{tab:io-befunde-3} fasst die Befunde zusammen; die Einzelaufrufe für Projekt~A stehen in Anhang~\ref{anhang:ergebnisse}.

Die beiden übrigen Aufrufe betreffen denselben Fehlerfall: Findet das Quellsystem keine Pakete, gibt es nach der Fehlermeldung zusätzlich einen Stacktrace der Node.js-Laufzeit aus, das Zielsystem nur die Meldung. Eine weitere Abweichung zeigte sich außerhalb der Aufrufmatrix: Wird das Werkzeug aus einem Verzeichnis gestartet, das über einen symbolischen Link erreicht wird, gibt das Quellsystem den aufgelösten und das Zielsystem den unaufgelösten Pfad aus. Dieses Verhalten ist in keiner Spezifikation erfasst und damit eine weitere, kleinere Spec-Lücke derselben Art wie die Datenflusslücke.

Für die beiden Defektklassen ergibt sich Folgendes. Die Verkabelungslücke trat auch im dritten Durchlauf nicht mehr auf. Die Datenflusslücke ebenfalls nicht: In Projekt~B weist das Zielsystem das private Wurzelpaket wie das Quellsystem als \texttt{UNLICENSED} aus, und \texttt{-{}-onlyAllow} bricht in beiden Systemen mit Exit-Code~$1$ und derselben Meldung ab. Damit ist die in Abschnitt~\ref{sec:datafluss-gap} offene Nachprüfung erfolgt. Zuschreiben lässt sich die Verbesserung der zweiten Skill-Iteration allerdings nicht eindeutig, weil sich zwischen den Durchläufen auch Sprachmodell, OpenCode-Version, Code-Intelligence-MCP und weitere Skill-Vorgaben geändert haben. Zugleich beantwortet der Durchlauf die in Kapitel~\ref{konzeption} gestellte Frage, ob die Neuimplementierung ohne Rückgriff auf den Quellcode auskommt, für dieses Fallbeispiel weitgehend positiv: Der Builder arbeitete nur auf Spezifikation und Architektur, und die verbliebenen Abweichungen sind Randfälle. Die Symlink-Abweichung zeigt aber, dass die Spezifikation das Quellverhalten weiterhin nicht lückenlos erfasst.

\subsection{Grenzen der Aussagekraft} \label{sec:validitaet}

Die Befunde dieses Kapitels sind als explorative Einzelfallbeobachtung zu verstehen, nicht als empirischer Nachweis im strengen Sinn. Im Sinne der von \textcite{korn2026reportingprompting} geforderten Transparenz werden die wesentlichen Einschränkungen hier ausdrücklich benannt.

\textbf{Interne Validität.} Konzeption, Durchführung und Bewertung lagen in einer Hand; die Zuordnung zu den Befundklassen erfolgte manuell und ohne zweite unabhängige Bewertung. Jede Pipelinekonfiguration wurde nur einmal ausgeführt, obwohl LLM-Ausgaben nicht deterministisch sind; schon die Zahl der identifizierten Funktionalitäten schwankte zwischen acht und neun. Zwischen den Durchläufen änderten sich jeweils mehrere Faktoren zugleich (Skills, OpenCode-Version, im dritten Durchlauf zusätzlich Sprachmodell und Code-Intelligence-MCP), sodass sich Verbesserungen keiner einzelnen Änderung sicher zuschreiben lassen. Die zweite Skill-Iteration wurde zudem in Kenntnis des konkreten Fehlers entworfen; ob sie über diesen Fall hinaus wirkt, ist offen. Schließlich fehlt eine Vergleichsbedingung: Es gab keinen Durchlauf ohne Spezifikationsebene, etwa eine direkte Übersetzung durch dasselbe Modell. Die Arbeit kann deshalb zeigen, dass der spezifikationsgetriebene Weg zu einem verhaltensgleichen Zielsystem führen kann, nicht aber, dass er einer direkten Übersetzung überlegen ist.

\textbf{Konstruktvalidität.} Die Befundklasse \emph{semantisch identisch} ist schwächer als die in Abschnitt~\ref{sec:qualitaet-code} definierte I/O-Äquivalenz. Im zweiten Durchlauf prüften einzelne Vergleichsfälle nur Teilaspekte, etwa bei F-004 nur Schema und Schlüsselbenennung, und von den Ausgabeformaten wurden nur JSON, CSV und Markdown verglichen. Der dritte Durchlauf wurde byteweise und über alle fünf Formate geprüft, deckt aber ebenfalls nur einen Ausschnitt des Eingaberaums ab: zwei Projekte und 62 Aufrufe. Nicht geprüft wurden unter anderem zyklische Abhängigkeiten, fehlerhafte Manifeste und Kombinationen vieler Flags. Die Referenzausgaben innerhalb der Pipeline waren statisch hergeleitet und nicht aufgezeichnet.

\textbf{Externe Validität.} Untersucht wurde ein einziges, vergleichsweise kleines CLI-Werkzeug mit einer festen Sprachkombination (Node.js nach Go). Ob sich die Befunde auf größere Systeme, andere Domänen oder andere Sprachpaare übertragen lassen, bleibt offen.

\textbf{Reproduzierbarkeit.} Agentenprofile, Skills und Konfiguration sind im PoC-Repository versioniert; Modell- und Werkzeugversionen der ausgewerteten Durchläufe dokumentiert Tabelle~\ref{tab:versuchsumgebung}. In den ersten beiden Durchläufen wurde das Quellsystem jedoch über \texttt{npx -{}-yes license-checker} aufgerufen, also in der zum Ausführungszeitpunkt aktuellen npm-Version und nicht in einem festgelegten Stand. Im dritten Durchlauf war die Version festgelegt, und das Vergleichsskript ist im Anhang dokumentiert. Die Rohausgaben der ersten beiden Durchläufe sind nicht archiviert.

Die Ergebnisse der Evaluation fließen in die abschließende Bewertung und den Ausblick in Kapitel~\ref{fazit} ein.
